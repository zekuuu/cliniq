# CLAUDE.md — Start Here

You are working on **CLINIQ: Intelligent Clinic Tracking and Monitoring System**, a clinic tracking system for Mendez Christian Academy (a Philippine private school, ~900 students, one nurse, one shared workstation, LAN-only deployment). This file is the entry point — read it before touching any code or documentation.

## Before you start any task

0. **Read the whole live repo before editing the knowledge base — not a spot-check.** The repo is https://github.com/zekuuu/cliniq; a `git clone` gives you every file and the full history, and it is the only reliable way to see all of it. Read the current tree and `git log` on **every branch** (real work can live on a feature branch such as `feature/clinic-overview-dashboard`, not just `main`). Your working copy can be stale relative to GitHub, and GitHub can be stale relative to unpushed local edits. This has already caused real damage on this project: documentation exports were copied over live work several times and silently reset progress — the `Frontend-Loop-Engineering.md` checklist dropped from 52 checked boxes to 0, and agent-written entries in the Changelog, Issues-and-TODOs, and Development-Phases were lost. It was recoverable only because the history was in git; anything an agent wrote but had not yet committed was gone. So: (a) for every file you change, start from the live version and change only what you meant to change; (b) files that carry progress or shared state — the checklist in `Frontend-Loop-Engineering.md`, `Changelog.md`, `Issues-and-TODOs.md`, and the skills in `.claude/skills/` (agents create and edit them) — are owned by the live repo: **merge into them, never regenerate or replace them from an export**; (c) `CLINIQ-Knowledge-Base/08-Logs/Agent-Sessions/` is the only append-only area (new files, never edited), so it is the only part of `08-Logs/` where reconciliation is unnecessary.

0a. **Separately: if you're a human copying a zip export of this project (generated by a chat session with an AI) into your actual project folder, never copy `frontend/` or `backend/` from that zip once real code exists in your project — and never copy the progress-state files named in Step 0(b).** Exports made from September 28, 2026 on leave the code folders out entirely, so there is nothing there to overwrite; an older export may still contain skeleton `frontend/` and `backend/` folders (or `cliniq-frontend/` and `cliniq-backend/`, their names before the September 28 rename), and the same rule applies to them. Extracting a zip on top of real, built code would overwrite and destroy it, not just replace something stale. Safe to copy from an export: knowledge-base files that carry no progress state, `AGENTS.md`, `CLAUDE.md`, `README.md`, and `LICENSE`. **Not** `.claude/skills/` — agents create and edit those skills now, so exports no longer include them. When in doubt, diff the export against the live repo first and copy only the files that differ for a reason you recognise.

## While you work

- Follow the architecture in `CLINIQ-Knowledge-Base/02-Architecture/` and the conventions in `CLINIQ-Knowledge-Base/04-Development/Coding-Conventions.md`.
- **Check `CLINIQ-Knowledge-Base/04-Development/Skills-Setup.md` for the current, full list of bespoke CLINIQ skills before building a new screen or mutation** — don't rely on any specific skill being named here, since this list is exactly the kind of thing that goes stale the moment a new skill is added and this file isn't updated in the same breath. As of this writing there are three: `cliniq-display-privacy`, `cliniq-audit-trail`, `cliniq-interactive-states` — but check the actual file, not this sentence, since this sentence is a snapshot, not a live source.
- **Component skills — create only for reusable cross-page patterns.** Consider a component skill only when the component is already reused, or is reasonably likely to be reused, across many pages (for example, search bars, dropdowns, buttons, date pickers, tables, or modals). Do not create one merely because a component is shared, major, or lives in `frontend/src/components/`.
  1. **Look for its skill first when the pattern is cross-page.** Check `.claude/skills/` for `cliniq-<component>-patterns`, reading only each skill's `name` and `description` (don't open them all).
  2. **None exists → create one only when it is likely to recur across many pages.** Base it on the user's stated preferences or prompt for that component, plus what `Design-System.md` already says. Record only what the user asked for; don't invent visual rules. Follow the format of `cliniq-dropdown-patterns` — a `description` that says when to apply it, the rules, and where the shared component lives — and reference `cliniq-interactive-states` instead of repeating it.
  3. **One exists → compare it when the request changes the reusable pattern.** Wherever the request and skill differ, treat the request as the new rule: edit the skill and shared component together so it holds for future uses, and update existing uses unless the user said future builds only. A page-specific request ("just on this screen," "only here") is implemented locally and leaves the skill alone. If a change conflicts with `Design-System.md` (a token, a contrast rule), apply it, flag it, and update the design system if the change is system-wide — never let the two drift.
  4. **Say it and log it.** When a skill is created or edited, state what differed and what changed (old → new), so the user can veto it. Then add an `Agent-Sessions/` entry, a Changelog row, and a row in `Skills-Setup.md`.
- Don't change technology choices without approval (see `CLINIQ-Knowledge-Base/06-Decisions/`).
- Don't modify features or files unrelated to your task.
- Write tests where applicable (`CLINIQ-Knowledge-Base/05-Testing/Test-Strategy.md`).
- **Every feature or prompt-driven change gets documented** — this project's working rule, not just a suggestion. If a person's prompt or request led to a decision or a change, that's exactly what belongs in the agent log below.
- **Be cost-conscious — this is a real, standing instruction, not a suggestion:**
  - Prefer a mid-tier model for pattern-following work (most of Phase F2's screens, once the 5 reference screens establish the patterns) and reserve the most capable model for genuinely foundational or ambiguous work (the reference screens themselves, Phase 0's reasoning, an unclear Phase 2 Audit finding).
  - Don't re-run `Frontend-Loop-Engineering.md`'s Phase 0 (Changelog/Decisions/Issues/skills read-through) more than once per continuous session — only redo it when starting a genuinely fresh session or after a real gap, not before every individual screen.
  - Edit files surgically (a targeted patch to the specific line/section that changed) rather than rewriting a whole file to make a small change — checking one box in a 200+ line checklist should cost a few lines of diff, not the whole file re-output.
  - Prefer a deterministic tool over an AI reasoning pass wherever one exists: run the actual test suite instead of re-verifying by inspection, use an accessibility CLI (e.g., axe-core) for contrast/ARIA checks instead of eyeballing them. This project's own precedent: the SRS diagrams were validated by actually running them through Mermaid's parser, not just visually inspected. (No formatter/linter is prescribed by this project — the team uses its own; don't introduce one as part of "being efficient.")
  - **Do not use Microsoft Edge for testing or verification.** Never launch Edge, connect to Edge's CDP interface, use headless Edge, or create Edge browser profiles/screenshots as test artifacts. Prefer the deterministic test suite and source-level checks; when a live browser check is explicitly necessary, use the existing Playwright/Chromium tooling instead and keep any temporary artifacts outside the repository.
  - Not every change needs the full Phase 0→1→2 process — a one-line copy fix or a correction to an already-audited screen's known value doesn't need a fresh Phase 0 and a full Countercheck. Use judgment on scale, but don't skip the process for anything that actually touches a documented requirement, a shared component, or cross-screen behavior.

## Timestamps — required on every log entry, changelog line, and ADR

Every entry you write — a session log, a changelog line, an ADR's Date field — must carry the **actual day of week, date, and time**, pulled from your real system clock at the moment you write it (e.g. `date "+%A, %B %d, %Y — %H:%M"` in bash, or whatever equivalent your environment gives you). Never estimate, round, or omit it, and never leave a placeholder. If your environment genuinely has no clock access, say so explicitly in the entry rather than guessing a value — an honest gap is fine; a fabricated timestamp is not.

## Source of Truth (conflict resolution)

1. Canonical documents (Project Plan, Modules & Features, Frontend Context Brief, Frontend Design Reference, Related Systems Review) — authoritative for **what** the system should do
2. `CLINIQ-Knowledge-Base/06-Decisions/` — authoritative for **how** it's being built
3. Current code + `CLINIQ-Knowledge-Base/02-Architecture/` — authoritative for what **currently exists**
4. `CLINIQ-Knowledge-Base/08-Logs/` — historical context, not itself current truth
5. Temporary notes, scratch work — never authoritative
6. AI-generated suggestions — never auto-promoted; only real once approved into `CLINIQ-Knowledge-Base/06-Decisions/`

A newer approved decision always overrides an older one. AI suggestions are not requirements until a person approves them.

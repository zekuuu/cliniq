# Canonical Documents

These five remain the authoritative source for requirements/scope — this vault distills and points to them, never replaces them. Keep them in the repo (e.g. a `/docs` folder alongside `/frontend` and `/backend`) so they travel with the code. Full copies of all five are already inside `09-References/Canonical-Documents/` — the descriptions below tell you what's actually in each one so you know which to open, rather than opening all five every time.

1. **CLINIQ Project Plan** (Revision 2.6). Sections: 1 — Problem Domain (statement of the problem, background, objectives, significance/scope); 2 — Project Organization (external interfaces, internal structure, roles, deliverables); 3 — Review of Existing Alternatives (systems reviewed, feature comparison tables, what it means for CLINIQ); 4 — Approach (theoretical framework, rationale, technologies); 5 — System Design (requirements, resources, system overview, risk assessment); 6 — Project Timeline (Gantt chart, work breakdown structure); 7 — Budget Allocation (estimated costs, total). Also carries the full Document Change Control revision history (every change ever made to the plan, with reasoning).

2. **CLINIQ Modules & Features.** The complete module/submodule breakdown — all modules (5 baseline: User Management, Student Records, Clinic Visit Monitoring, Emergency Response, Reports Generation; enhancements: First-aid checklist, Inventory Tracker, Clinic Overview Dashboard, Backup Verification Assistant, Audit Log Viewer), every operation within each tagged with who can access it. Also contains: the Audit Trail cross-cutting rules, the Access Summary table, Recommendations for Future Consideration (UPS, backup layer), Open Questions pending client input, and the Future Development section (Canteen Staff access, full school-events calendar). **Fully mirrored in `01-Requirements/Features/Module-Overview.md`.**

3. **CLINIQ Frontend Context Brief.** The full technical/functional frontend spec for an AI coding agent: project context, tech stack conventions, user roles/permissions (with the display-privacy rule), the complete ~37-screen inventory, data entities the frontend should expect, key interaction flows, the full Design & UX Guidelines (typography, color system with real sampled hex values and computed contrast ratios, buttons, layout, forms, navigation, accessibility, feedback states, modals, motion, consistency, visual hierarchy), non-functional requirements, and explicit out-of-scope items. **Screen inventory and design guidelines mirrored in `03-Design/`.**

4. **CLINIQ Frontend Design Reference.** A companion to #3, written for a *designer* rather than a coding agent: the same design system, condensed, plus full deep-detail on the reference screens (Clinic Overview Dashboard, New Visit Entry, Student Profile, two-stage Incident Entry; Reference 4 was removed with the QR feature, ADR-027) chosen because together they exercise nearly every UI component the system needs — and a mapping table for which reference screen every other screen should follow. **Fully mirrored in `03-Design/Reference-Screens.md`.**

5. **CLINIQ Review of Related Systems.** The researched comparison against 10 existing systems: SEAIT SCMS, E-Konsulta, SurgiCare, ClinicSync, ISU–San Mariano CMS, EduHealth System, Medical Tracker, LinkHMS, CareMonkey, and iSAMS by IRIS — full profile per system (type, origin, reference citation, complete feature list), a single master feature-comparison table covering every distinct feature found across all systems, a synthesis of what the comparison means for CLINIQ's own design choices, and narrative one-paragraph summaries of each system. This one is intentionally **not** duplicated elsewhere in the vault — it's a large, self-contained research document; open it directly at `09-References/Canonical-Documents/CLINIQ_Review_of_Related_Systems.md` when you need it.

**When the vault and a canonical document disagree:** the canonical document wins, and the vault should be corrected to match — unless the disagreement reflects a decision made *after* the canonical document was last updated, in which case both need updating together (see `06-Decisions/`, and `AGENTS.md`'s instruction not to let them drift apart).

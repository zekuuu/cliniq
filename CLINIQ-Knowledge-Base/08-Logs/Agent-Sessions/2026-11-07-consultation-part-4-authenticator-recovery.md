## For the backend branch

Copy these names and rules into the backend documents (ERD, Data Dictionary, API contract) on the `backend` branch; log the work in `Backend-Issues-and-TODOs.md` there.

1. **Labels versus data (ADR-070).** Screens say "Symptom(s)" and "Released to"; the data keeps `complaint`, `extraComplaints` and `collectedBy` (name, relationship, time). When the relationship is "Other", the frontend sends who it was as the `relationship` text (for example "Neighbour"), never the word "Other". No column renames.
2. **`inventory_items.usedFor`** (ADR-071): a list of symptom option ids, which are the visit complaint-type labels (for example "Headache"), stored in the option list's order, optional, no repeats, unknown values refused. Staff edit it on the item form; it is audited as "Updated commonly used for" (field name only). A save that omits it keeps the existing tags. It only orders the Visit form's picker; it never blocks or hides an item.
3. **School-year settings** (ADR-072): `schoolYearStartMonth` (1–12, default 6), `schoolYearStartDay` (1 to the month's days, February 28, default 15), `schoolYearEndMonth` (default 4), `schoolYearEndDay` (default 14); the end may not equal the start. Staff only; audited by field name. A school year "YYYY–YYYY" (en dash) runs from the start date to the day before the next start.
4. **Archive fields on students and staff** (ADR-072): `archivedAt` (datetime), `archiveReason` (text, required, up to 80 characters), `archivedSchoolYear` (the label at archive time, stored, never recomputed). All three on an archived record, none on an active one. The manual archive takes the reason; the student import writes "Not on the new list"; the staff import archives nobody (ADR-069). Reports and the audit tab derive their year from dates and the current settings. Backup runs carry `locationNames` (the labels at run time), and a backup location is never edited (add a new one, disable the old).
5. **Authenticator fields** (ADR-073), per user: `totp_secret` (**encrypted at rest**, never returned after setup), `totp_confirmed_at`, `recovery_code_hashes` (8 at setup, **slow hash** such as bcrypt or argon2, each removed when used). Endpoints, all for the signed-in user except the last two: start setup (returns the secret and otpauth URI once; replacing needs a current code or a recovery code), confirm setup (first code; returns the 8 codes once), turn off (needs a code), status (enabled, codes left); and, unauthenticated, verify recovery (username + code or recovery code, returns a short-lived one-time token) and reset password (token + new password by the Change Password rules; clears a pending forced change). Codes: RFC 6238, SHA-1, 30 s, 6 digits, ±1 step.
6. **Error behaviour:** every failed recovery (unknown username, wrong code, no authenticator, disabled account) returns the same message, and counts toward the sign-in lockout (5 failures, 30 minutes, ADR-015), with the same lock response as sign-in.
7. **Audit actions** (by action and user only, never a code, secret or password): "Set up authenticator", "Replaced authenticator", "Turned off authenticator", "Used a recovery code", "Reset password with authenticator", and the usual "Changed password". A lockout at recovery is logged like the sign-in one, "(password recovery)".
8. **Dropped:** the email password reset of ADR-048. No email address is needed on accounts; the "Backend: email password reset" entry can be closed there.
9. **Admin-account risk:** nobody can reset the Administrator's password. If the Admin never sets up the authenticator (or loses both the phone and the recovery codes) and forgets the password, account management is locked. The backend should keep a documented, offline break-glass procedure (for example a console command on the clinic computer) and the Admin should set up the authenticator at handover.
